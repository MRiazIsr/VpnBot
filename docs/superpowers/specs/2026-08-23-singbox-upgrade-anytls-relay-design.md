# Плечо RuVDS→Hetzner: relay, AnyTLS и Hysteria2 — Design

## Цель

Перевести трансграничное плечо RuVDS→Hetzner с ядерного DNAT на туннель,
которым можно управлять: с мультиплексом, с контролем перегрузки, с
переключением между несколькими транспортами по фактической скорости.

## Поправка к исходной формулировке

Задача ставилась как «снять тяжёлую маскировку с длинного плеча». К этой схеме
формулировка не применима: **на плече RuVDS→Hetzner нет никакой маскировки.**
Там ядерный DNAT — `nft` переписывает адрес назначения, и клиентский
Reality-поток идёт через границу байт в байт тем же. Ни второго шифрования, ни
TLS-in-TLS, ни разбора потока. Дешевле физически некуда.

Поэтому AnyTLS или Hysteria2 здесь **добавляют** первый слой, а не снимают
второй: вырастет и CPU на RuVDS, и число байт на проводе.

Делать это стоит, но ради другого:

* **Мультиплекс.** Сейчас каждое клиентское соединение платит полное трансграничное TCP-рукопожатие. На MTProto-туннеле это уже измерено: 136 мс → 29 мс на соединение, уникальных TCP через границу 220 → 78 за 5 минут. На VLESS соединений на порядок больше.
* **Контроль перегрузки.** Brutal (Hysteria2) не сваливается в loss-based backoff на плече с наведёнными потерями. DNAT отдаёт потери клиентскому TCP, который честно тормозит.
* **Один поток вместо россыпи рукопожатий.** Сейчас видно N сырых Reality-хендшейков RU→DE — ровно тот паттерн, по которому ловили в июне 2026.
* **Port hopping** — устойчивость к блокировке по порту, которой у DNAT нет.

## Замеры, на которых всё построено (23.08.2026)

Проверено по SSH на обоих хостах, а не взято из доков.

**Живая схема — DNAT-релей.** Тройной backhaul не развёрнут ни на одном хосте:
нет `wg-quick@wg1`, `backhaul-probe`, `sing-box-bhws`, `frps`, нет SOCKS5 на
1108x/1109x.

```
Клиент ──▶ RuVDS 87.247.157.120
             ├─ 2053-2058, 4443, 8444, 8445, 8447 ──nft DNAT──▶ Hetzner
             ├─ 9443 ──nft redirect :29443──▶ reality-туннель ──▶ Hetzner:8765
             ├─ 443 ──nginx ssl_preread по SNI──▶ туннели / сайт-приманка
             └─ 2059, 2060, 8446 ──▶ локальный sing-box ──direct──▶ RU-выход
```

**Трансграничный UDP проходит в обе стороны:** RuVDS→Hetzner:51820 20/20 и
15/15; Hetzner→RuVDS 15/15 на оба адреса. Прежний вывод «UDP не ходит» строился
на нулях `wg0` и неверен — это локальный дефект конфигурации, не блокировка.
Отдельно: фильтр на 194.87.80.237 — **только TCP**, UDP на тот же адрес доходит.

**Пересборка sing-box не нужна.** Боевой бинарь — чистый апстрим
(rev `596291567f`, «Update AmneziaWG», 25.01.2026), никакого xhttp-патча в нём
нет. Проверено `sing-box check` прямо на нём:

| Конфигурация | Результат |
|---|---|
| `hysteria2` + salamander | принят |
| `hysteria2` + `server_ports` + `hop_interval` | принят |
| `anytls` + tls | принят |
| `anytls` + tls + reality + utls chrome | принят |
| `naive` outbound | `unknown outbound type` |
| `hysteria-realm` service | `unknown inbound type` |

Всё нужное для этой задачи бинарь умеет уже сегодня.

## Этап 0 — починить откат (блокирующий)

**Ничего из последующего не запускается, пока откат не работает.** Сейчас он не
работает, и это проверено.

### Дефект

`promote.sh:73` снимает снимок через `iptables-save -t nat`, а боевой DNAT живёт
в nftables (`table ip relay`). На машине `iptables v1.8.4 (legacy)`, который
nftables-правила не видит:

```
iptables-save -t nat      → 0 правил, пустые цепочки
nft list table ip relay   → 10 правил dnat
```

Снимок пустой. `do_rollback()` делает `iptables-restore -T nat` этим пустым
снимком — no-op. При этом удаляет правила promote корректно, через `nft delete`.
Итог: односторонняя дверь с бутафорской страховкой.

### Что чинится

1. Снимок: `nft list table ip relay > /etc/backhaul/relay-nat.nft`, плюс полный `nft list ruleset` рядом.
2. **Проверка непустоты снимка перед любым изменением.** Пустой снимок — abort. Один этот шаг поймал бы текущий дефект.
3. Откат: `nft delete table ip relay 2>/dev/null; nft -f /etc/backhaul/relay-nat.nft`.
4. Восстановление DNAT в `do_rollback()` идёт **первым и безусловно** — до всякой работы с конфигами и до `sing-box check`. Сломанный конфиг не должен мешать вернуть трафик.
5. Проверка, что таймер автоотката реально взведён (`systemctl is-active`), **до** удаления первого правила. Не взведён — abort.
6. `CONFIRM_SEC` на первый перевод — 300 с вместо 900.

### Почему откат здесь дёшев

DNAT в PREROUTING срабатывает раньше поиска локального сокета. Значит DNAT и
слушатель relay **сосуществуют**: пока правило есть — выигрывает оно; удалили —
трафик проваливается в relay. Поэтому и перевод, и откат это только правки
ruleset: никаких рестартов сервисов, relay работает непрерывно в обе стороны.

## Откат: четыре уровня

### Уровень 1 — аварийный рычаг, работает уже сегодня

```
systemctl restart nftables
```

Юнит устроен как `ExecStop=nft flush ruleset` + `ExecStart=nft -f /etc/nftables.conf`,
а файл содержит все три боевые таблицы (`relay`, `mss_clamp`,
`mtproxy_smart_syn_alt`). То есть команда возвращает ровно боевое состояние,
включая MSS-клемпинг, за один шаг. Не зависит ни от скриптов backhaul, ни от
Go-бинарей, ни от валидности конфигов.

Условие, которое надо удержать: **`promote.sh` не имеет права писать в
`/etc/nftables.conf`.** Только `--confirm`, и только после того, как оператор
проверил живым клиентом.

Оговорка: `systemctl reload nftables` небезопасен — в файле нет
`flush ruleset`, и `nft -f` поверх живых таблиц задублирует правила. Только
`restart`.

### Уровень 2 — `promote.sh --rollback`

Точечный возврат `table ip relay` из снимка, без флеша остального ruleset.
После починки этапа 0.

### Уровень 3 — таймер бездействия

`backhaul-promote-rollback.timer` вызывает `--rollback` через `CONFIRM_SEC`,
если оператор не подтвердил. Взводится **до** первого изменения.

### Уровень 4 — перезагрузка откатывает, а не накатывает

`/etc/nftables.conf` во время перевода не трогается, поэтому холодный ребут
восстанавливает DNAT. Это намеренно: 30.07.2026 перезагрузка молча поменяла
живой путь и вызвала аварию. Здесь перезагрузка детерминированно ведёт в
безопасную сторону.

## Этап 1 — relay и emergency на staging

Разворачивается написанное: `sing-box-relay` на RuVDS (`direct` inbound,
селекторы), `backhaul-monitor`, плечо emergency (`ssh -D` с RuVDS на Hetzner,
пользователь `backhaul` с `PermitOpen` строго на backend-порты). Установка на
**staging-портах** (`порт + 30000`), прод не затрагивается.

Плечи primary (израильский узел) и secondary (Yandex Cloud) в этот этап не
входят и помечены `disabled`.

### Дефект, который надо исправить до перевода

`docs/backhaul-triple.md` включает в relay-список RU (2059), RU-TCP (2060) и
RU-STLS (8446). Relay гонит всё на Hetzner, а эти три существуют затем, чтобы
выходить **с русского адреса** — сейчас их обслуживает локальный sing-box с
`route.final=direct`. Через relay они станут немецкими, и смысл профилей
пропадёт.

Вдобавок док написан до смены адресов: его критерий отбора —
`ServerAddress = 194.87.80.237`, а у RU-профилей в базе `87.247.157.120`. По
собственному правилу дока они в relay попадать не должны, а в списке стоят.

Исправление: RU, RU-TCP, RU-STLS исключаются из `RELAY_VLESS_PORTS`.

## Этап 2 — канареечный перевод одного порта

`promote.sh` сейчас переводит все порты одним циклом. Это лишний риск: relay уже
слушает, проверить схему можно на одном порту.

Первым переводится **DE-WL (2058)** — не самый нагруженный профиль. Оператор
проверяет живым клиентом, смотрит `stream.log` и логи relay, и только потом
переводятся остальные.

Добавляется параметр `--only <порт>`.

## Этап 3 — ярусы AnyTLS и Hysteria2

Ярус в этой архитектуре — процесс, отдающий SOCKS5 на `127.0.0.1`; relay
выбирает между ярусами селектором. Значит новый транспорт — это новый адаптер,
а не переделка relay.

**Выбирать между AnyTLS и Hysteria2 не нужно.** `backhaul-monitor` гоняет по
128 КБ вверх и вниз через каждый ярус независимо от того, какой активен, и
переключается по фактической скорости с гистерезисом. Заводятся оба, решает
замер.

Порядок — **AnyTLS первым**: он TCP, а на этом плече TCP-подобная форма имеет
послужной список (в мае 2026 здесь умер fake-TLS и выжил reality). Hysteria2
вторым: замер UDP от 23.08 — это 35 пакетов, а устойчивый многомегабитный QUIC
RU→DE через хостинговый ASN непроверен.

```
RuVDS                                          Hetzner
sing-box-bh-anytls  SOCKS5 (свой порт) ──anytls──▶ inbound anytls  ──▶ backend
sing-box-bh-hy2     SOCKS5 (свой порт) ──hy2   ──▶ inbound hysteria2 ──▶ backend
backhaul-fssh@*     SOCKS5 (свой порт) ──ssh -D──▶ sshd (PermitOpen) ──▶ backend
```

Порты SOCKS5 берутся из существующей схемы `Tier.SocksPort` — по отдельному
порту на класс сервиса, чтобы VLESS и MTProto не делили поток.

### Куда ложатся ярусы

Имена ярусов в коде валидируются по фиксированному списку
(`TierPrimary/TierSecondary/TierEmergency`, `service/backhaul/config.go:45-49`),
то есть добавить четвёртый нельзя без правки кода.

Правки и не требуется: слоты `primary` и `secondary` **свободны** — они были
зарезервированы под израильский узел и ВМ в Yandex Cloud, которых нет. AnyTLS и
Hysteria2 занимают их, `emergency` остаётся за `ssh -D`. Меняется только
содержимое ярусов, не их количество.

Но имена станут врать: «primary» будет означать AnyTLS, а не резидентный узел.
Поэтому в этап входит переименование констант в транспорт-нейтральные (`tier1`,
`tier2`, `tier3` при сохранении семантики `Rank`) либо в осмысленные по
транспорту. Решается при написании плана; важно, что `Rank` задаёт приоритет и
от имени не зависит.

### Противоречие, которое решается осознанно

В `service/backhaul/singbox.go:16-18` записано намеренное свойство: «никакого
multiplex на socks-outbound'ах: каждое клиентское соединение едет отдельным
TCP-потоком, общего мультиплекса нет». Hysteria2 делает всё плечо одним
QUIC-соединением с потоками внутри — ровно то, что было запрещено.

Запрет не случаен: общий поток означает head-of-line blocking и общую судьбу
всех пользователей. Но прецедент ограниченного компромисса есть — на
MTProto-туннеле стоит `max_streams: 8` именно чтобы ограничить радиус. Здесь
принимается то же решение, и оно фиксируется в комментарии рядом со старым
запретом, чтобы следующий читатель не счёл это недосмотром.

## Вне объёма

* **Пересборка sing-box** — не нужна, всё требуемое бинарь умеет (проверено).
* **NaiveProxy** — требует `with_naive_outbound` и `libcronet.so`, то есть своей сборки. К этой задаче отношения не имеет; отдельным решением.
* **Hysteria Realms и ярус primary** — Realms решает CGNAT на стороне сервера, а в этой схеме проблемы CGNAT нет: `frpc` звонит наружу сам (`docs/backhaul-triple.md:95`). Настоящим блокером был отказ RuVDS принимать входящий TCP, но это свойство адреса 194.87.80.237, а на 87.247.157.120 вход открыт. Ярус primary требует физической машины в Израиле, которой нет.
* **Ярус secondary (Yandex Cloud)** — до создания ВМ.
* **Схлопывание портов на 443 через `ssl_preread`** — отдельно.
* **Починка `wg0`** — путь чист, но WireGuard в новой схеме не используется.

## Открытые вопросы

3. Нужен ли `max_streams` и какой у AnyTLS-яруса — по замеру, а не заранее.
