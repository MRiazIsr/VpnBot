# HEALTH ALARM — дизайн (спека)

Дата: 2026-05-19. Статус: на ревью пользователя (до плана реализации).

## 1. Цель и проблема

Админ должен узнавать о сбое **раньше юзеров**: какие инбаунды/сервисы
отвалились или начали деградировать. Мотив — инцидент 15–19 мая 2026:
порт MTProto был TCP-OPEN всё время, payload молча дропался ТСПУ; админ
узнал от пользователей. Текущий `CheckAllInboundPorts()` (только TCP-connect)
такой сбой **не ловит**.

Дополнительно: одна кнопка на уведомлении о **восстановлении**, чтобы
разослать всем юзерам, что связь снова работает (во время сбоя юзеров не
дёргаем — только админ).

Видит health-уведомления **только админ** (`bot.AdminID`).

## 2. Скоуп

В скоупе: фоновый детектор, машина состояний OK/DEGRADATION/DOWN,
уведомления админу на переходах с дедупом/гистерезисом, inline-кнопка
рассылки шаблона всем активным юзерам.

Вне скоупа (YAGNI): синтетические клиент-пробы per-transport, графики/история,
внешние алерт-системы (PagerDuty и т.п.), авто-починка, глубокий telemt
timeout-rate сигнал (фаза 2). Перевод nft-генератора — **отдельная задача**
(см. `docs/ruvds-nftables-migration.md` §7), не часть этой спеки.

## 3. Архитектура

Разделение «обнаружение ↔ доставка»:

- **`service/health`** (новый пакет, без зависимости от telebot — тестируемый):
  - сбор сигналов, машина состояний, вычисление переходов;
  - экспортирует тип результата (список сервисов с состоянием + причинами)
    и функцию одного цикла оценки `Evaluate(prev) -> (curr, transitions)`.
- **`bot/healthalarm.go`** (новый файл, не раздуваем `bot.go` 27КБ):
  - goroutine-цикл с тикером (интервал из конфига);
  - держит предыдущее состояние, зовёт `health.Evaluate`;
  - на переходах шлёт DM админу + inline-кнопку;
  - обработчик кнопки «📢 Оповестить всех» — рассылка с подтверждением.

Запуск goroutine — из существующей `bot.Start(...)` (там уже есть
`tele.Bot`, `AdminID`, доступ к `database.DB`).

## 4. Сигналы детекции — ТОЛЬКО «коннект проходит / не проходит»

**Жёсткое правило: объём трафика НЕ является сигналом.** Ночью юзеров мало,
трафик падает — это норма, не авария. Триггер — только **активный отказ
прохождения соединения**, устойчивый к времени суток.

Per enabled-инбаунд и для telemt (если включён):

1. **TCP/цепочка** — существующий `service.CheckAllInboundPorts()`
   (RuVDS-цепочка + прямой Hetzner). Даёт: порт закрыт / частичный отказ
   (одно плечо живо, другое нет).
2. **Активная проба прохождения** — на каждом цикле детектор сам
   инициирует пробное соединение по цепочке и проверяет, что оно
   **проходит насквозь** (доходит валидный отклик), а не «порт открыт, а
   payload в тишине» (майская сигнатура). Не зависит от наличия живых
   юзеров → ночь не даёт ложняка. Реализация пробы per-сервис уточняется
   в плане (минимально достаточная, не полноценный клиент).
3. **Доля неуспеха реальных попыток** (где доступно, напр. telemt): не
   абсолютное число, а **ratio** failed/total. Ночью попыток мало, но
   ratio≈0 = OK; сломано = ratio высокий независимо от объёма.

Трафик-дельта может использоваться **только как вторичное подтверждение
рядом с активным отказом**, никогда сам по себе и никогда как триггер.

telemt: именованный сервис, те же сигналы (порт + активная проба / ratio).
Глубокий telemt timeout-rate — фаза 2.

## 5. Машина состояний

Состояния per-сервис: `OK / DEGRADATION / DOWN`.

| Состояние | Условие (только «коннект проходит/нет», без объёма трафика) |
|---|---|
| **OK** | TCP жив И активная проба проходит насквозь |
| **DEGRADATION** | Ранний признак потери коннекта: активная проба **не проходит** (порт открыт, payload не доходит), ИЛИ частичный отказ (RuVDS-цепочка ок, прямой Hetzner нет — или наоборот), ИЛИ ratio неуспеха попыток выше порога, ИЛИ 1-й провальный цикл (DOWN ещё не подтверждён гистерезисом). Срабатывает немедленно. |
| **DOWN** | Жёсткий/устойчивый отказ: порт закрыт ИЛИ активная проба не проходит, удержано ≥ M циклов (гистерезис) |

- **DEGRADATION** срабатывает немедленно (смысл фичи — скорость; ранний
  сигнал до полного падения).
- **DOWN** требует M подряд подтверждений (гистерезис, дефолт M=2) —
  одиночный сетевой блик не паникует.

## 6. Уведомления (только админ, дедуп по переходам)

Цикл раз в N сек. Сообщение отправляется **ровно один раз на переходе**:

| Переход | Сообщение | Кнопка рассылки? |
|---|---|---|
| `OK → DEGRADATION` | ⚠️ «Деградация / теряем коннект: \<список сервисов + причины\>» | НЕТ (только админу) |
| `* → DOWN` | 🔴 «Отвалилось: \<список + причины + с какого времени\>» | НЕТ (только админу) |
| `* → OK` (восстановление) | ✅ «Восстановлено: \<список\>» + **кнопка «📢 Оповестить всех»** | **ДА** |
| `DOWN → DEGRADATION` | без отдельного уведомления (ждём полного OK; иначе шум) | — |

Во время сбоя — **только админу**, без рассылки юзерам (вдруг само
отлежится; не паниковать людей преждевременно). Рассылка всем — осознанное
действие на **подтверждённом восстановлении**.

Адресат — `bot.AdminID`, больше никто. Дедуп: пока состояние не сменилось —
повторно не шлём. Состояние держится в памяти goroutine (переживать
рестарт не требуется — после рестарта первый цикл заново оценит).

## 7. Конфиг

Параметры (дефолты разумные, работает из коробки):

- `interval` — период цикла (дефолт 60с)
- `down_hysteresis` M — циклов подряд для подтверждения DOWN (дефолт 2)
- `probe_timeout` — таймаут активной пробы прохождения (дефолт 5с)
- `fail_ratio_pct` — порог доли неуспеха попыток для DEGRADATION там, где
  сигнал доступен (дефолт 50%)
- `enabled` — вкл/выкл фичи (дефолт on)

(Объёмных/трафиковых порогов нет намеренно — трафик не сигнал, см. §4.)

Хранение: строка в БД по образцу `TelemetConfig` (модель `HealthConfig`)
ИЛИ env. Решение детали — на этапе плана; интерфейс пакета от этого не зависит.

## 8. Кнопка «📢 Оповестить всех» (на восстановлении → OK)

- Inline-кнопка **только под уведомлением `*→OK` (восстановление)**.
- По нажатию: подтверждение «Разослать N активным юзерам?» (anti-misclick),
  кнопки Да/Отмена.
- При Да — рассылка всем `users.status = active` шаблона восстановления:
  > ✅ Связь восстановлена. Были перебои с подключением \<список сервисов из недавнего инцидента\> — сейчас всё работает.
  `<список>` подставляется из сервисов, что были в DOWN/DEGRADATION в этом
  инциденте (запоминаются на время инцидента, отдаются в момент `→OK`).
- Троттлинг рассылки под лимиты Telegram Bot API.
- Анти-дабл-клик: кнопка гасится/«рассылается…» после первого нажатия.
- Только админ может нажать (проверка `c.Sender().ID == AdminID`).

## 9. Тестирование

- `service/health` — юнит-тесты: моки сигналов → проверяем корректность
  переходов OK↔DEGRADATION↔DOWN, гистерезис M, дедуп (нет повторов),
  формирование списка причин. Без Telegram/сети.
- Доставка в боте — ручная проверка на живом стенде (telebot тяжело
  юнит-тестить; логика вынесена в service/health и протестирована там).

## 10. Открытые мелочи (решаются в плане, не блокируют)

- Точная модель хранения конфига (БД-строка vs env).
- Реализация активной пробы прохождения per-сервис (минимально
  достаточная: что шлём и что считаем «прошло» для reality/xhttp/raw/
  hysteria2/telemt) — ключевая деталь, прорабатывается в плане.
