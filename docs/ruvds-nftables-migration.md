# Замена iptables → nftables на RuVDS-релее (план на будущее)

> Статус: **план**, не выполнено. Документ написан после инцидента ТСПУ-дроп MTProto
> (19 мая 2026). К той аварии nftables отношения **не имеет** — это отдельный
> hardening. См. память проекта `tspu-rst-injection-relay-may2026`.

---

## 1. Зачем вообще менять. Конкретные боли (не абстрактные)

RuVDS-релей сейчас работает на **runtime-правилах iptables**, которые Go-приложение
(`service/portforward.go`) добавляет по SSH и сохраняет в `/etc/iptables/rules.v4`.
В ходе инцидента всплыли реальные дефекты именно этой схемы:

| # | Боль (наблюдалась вживую) | Последствие |
|---|---|---|
| 1 | **`netfilter-persistent` = failed** при загрузке (гонка xtables-lock, плагин `15-ip4tables` без `-w`) | После cold-reboot 15 мая nat-таблица **не восстановилась сама** — релей лёг, пришлось руками гонять rollback. Это и есть корневая хрупкость. |
| 2 | Правила добавляются по одному рантаймом (`AddForward`) | Нет атомарности: между «снёс DNAT» и «добавил REDIRECT» — окно, когда порт мёртв. Видели при cutover 19 мая. |
| 3 | `iptables v1.8.4 (legacy)` + UFW рядом | Два независимых пакетных движка на одной машине; правила в разных местах, тяжело рассуждать о порядке. Грабли: после REDIRECT 9443→29443 трафик начал рубиться о `INPUT policy DROP` UFW, пока не открыли 29443. |
| 4 | `iptables-save > rules.v4` как «персист» | Снимок мутабельного состояния. Если кто-то поправил правила и забыл `save` — ребут потеряет (ровно сценарий 15 мая). |
| 5 | Только TCP | UDP/Hysteria2 идёт мимо (через `vk-turn-client`). Логика проброса размазана по двум подсистемам. |

**Вывод:** менять стоит не «потому что iptables плохой», а чтобы убить боль №1 и №4
(ребут больше не теряет конфиг) и №2 (атомарность). nftables решает это «из коробки».

---

## 2. Что такое nftables — простыми словами

`iptables` — это **набор отдельных команд**, каждая дёргает ядро по одной правке.
Состояние живёт в памяти ядра; «сохранение» — это сделать дамп текущего состояния
в файл и надеяться, что при загрузке кто-то его накатит (этот «кто-то» —
`netfilter-persistent` — у нас сломан).

`nftables` — это **один декларативный файл-описание всего фаервола** (`/etc/nftables.conf`),
который ядро применяет **атомарно одной транзакцией** (`nft -f`). Аналогия:
iptables — это править прод по одной SQL-команде в проде; nftables — это
задеплоить весь конфиг одним файлом, который либо применяется целиком, либо
не применяется вообще.

Чем лечит каждую боль:

| Боль | Как nftables закрывает |
|---|---|
| №1 персист сломан | Штатный `systemctl enable nftables` грузит `/etc/nftables.conf` при бутe. Никакого `run-parts`, никакой гонки lock. Файл — **источник истины**, не дамп. |
| №2 нет атомарности | `nft -f /etc/nftables.conf` — вся таблица заменяется одной транзакцией. Нет окна «порт мёртв». |
| №3 порядок/два движка | Один синтаксис, один инструмент. (UFW — отдельная история, см. §5.) |
| №4 персист = дамп | Конфиг **пишется руками/генератором как декларация**, а не снимается с живого состояния. |
| читаемость | `set`/`map`/`vmap` — список из 10 портов становится одной строкой, а не 20 правилами. |

## 3. Текущее состояние RuVDS (точный снимок 19.05.2026)

- `iptables v1.8.4 (legacy)` (бэкенд `iptables-legacy`, **не** `iptables-nft`)
- **`nft` НЕ установлен**, пакета `nftables` нет, `nftables.service` отсутствует
- UFW активен (на RuVDS — поверх legacy iptables), `INPUT policy DROP`
- `net.ipv4.ip_forward = 1`
- nat-таблица (то, что переносим):
  - `PREROUTING`: **REDIRECT 9443 → 29443** (это наш MTProto-туннель, терять НЕЛЬЗЯ)
    + 10× `DNAT --to 49.13.201.110:<порт>` для 443, 2053-2058, 4443, 8444, 8447
  - `POSTROUTING`: 10× `MASQUERADE` на 49.13.201.110 для тех же портов
  - (MASQUERADE для 9443 снят при cutover — туннель сам делает egress)

## 4. Перенос 1:1 в nftables (читаемо, через map)

Весь сегодняшний nat-блок RuVDS = один файл `/etc/nftables.conf`:

```nft
#!/usr/sbin/nft -f
flush ruleset

define HETZNER = 49.13.201.110

table ip relay {

    # порт → проброс на Hetzner. Добавить порт = одна строка в map.
    map dnat_ports {
        type inet_service : ipv4_addr . inet_service
        elements = {
            443  : $HETZNER . 443,
            2053 : $HETZNER . 2053,
            2054 : $HETZNER . 2054,
            2055 : $HETZNER . 2055,
            2056 : $HETZNER . 2056,
            2057 : $HETZNER . 2057,
            2058 : $HETZNER . 2058,
            4443 : $HETZNER . 4443,
            8444 : $HETZNER . 8444,
            8447 : $HETZNER . 8447
        }
    }

    chain prerouting {
        type nat hook prerouting priority dstnat; policy accept;

        # MTProto-туннель: 9443 → локальный sing-box-tunnel9443 (НЕ терять!)
        tcp dport 9443 redirect to :29443

        # остальные VPN-порты → Hetzner (одна строка вместо 10 правил)
        dnat ip to tcp dport map @dnat_ports
    }

    chain postrouting {
        type nat hook postrouting priority srcnat; policy accept;
        ip daddr $HETZNER tcp dport { 443, 2053-2058, 4443, 8444, 8447 } masquerade
    }
}
```

Сравни: 21 строка iptables-правил → один самодокументированный файл.
Добавить инбаунд = дописать строку в `map dnat_ports`, `nft -f` — атомарно.

> Замечание про порядок: REDIRECT 9443 стоит **до** `dnat ... map`, и 9443 в map
> отсутствует — двойного срабатывания нет. Это важное свойство, его надо сохранить
> в генераторе.

## 5. Грабли именно нашей среды (без этого миграция сломает прод)

1. **`nft` не установлен** → шаг 0 миграции: `apt-get install -y nftables`.
   Без интернета на RuVDS в нужный момент — заранее.
2. **UFW сосуществование.** UFW на RuVDS сидит на legacy-iptables и держит
   `INPUT DROP` + свои цепочки. Если включить `nftables.service` **в дополнение**
   к UFW — будут два независимых ruleset (legacy + nft), и наш REDIRECT-трафик
   снова упрётся в UFW INPUT, как 19 мая. Варианты:
   - (a) держать nftables **только для nat-таблицы** (`table ip relay`), а filter/INPUT
     оставить UFW. nat и filter — разные hooks, не конфликтуют. **Минимальный риск.**
   - (b) мигрировать и UFW-правила в тот же `nftables.conf` и UFW убрать — чище,
     но больше работы и риск отрезать SSH. Не на первом шаге.
   - Рекомендация: **(a)**. Плюс не забыть `nft ... ` эквивалент `ufw allow 29443/tcp`
     если уходим от UFW; пока UFW жив — правило 29443 уже есть, не трогать.
3. **REDIRECT 9443→29443 — это жизнь MTProto.** Любой `flush ruleset` без этой
   строки = мгновенное падение прокси. Должна быть в файле всегда.
4. **`iptables-legacy` vs `iptables-nft`.** Не смешивать: если поставить
   `nftables` и при этом оставить legacy-правила в `rules.v4` + сломанный
   `netfilter-persistent`, можно получить дубли. План: nft-файл становится
   единственным источником nat, `rules.v4`/`netfilter-persistent` для nat —
   вывести из игры (отключить `netfilter-persistent` или вычистить из rules.v4
   nat-секцию).

## 6. План миграции (поэтапно, обратимо, с гейтами)

Прод не трогаем, пока шаг не подтверждён.

0. **Подготовка (read-only/безопасно):** `apt-get install -y nftables`
   (НЕ enable). Сгенерить `/etc/nftables.conf` из §4. Проверить синтаксис:
   `nft -c -f /etc/nftables.conf` (только проверка, не применяет).
1. **Сухой прогон:** `nft -f /etc/nftables.conf` применяет nat-таблицу `relay`
   в дополнение к живым legacy-правилам. Проверить: `nft list table ip relay`,
   счётчики растут, MTProto (44 сессии) и VPN-порты живы. Если что — `nft delete
   table ip relay` мгновенно убирает только наш кусок.
2. **Снять legacy-nat:** очистить legacy `PREROUTING/POSTROUTING` (бэкап есть
   в `/root/rollback_9443_dnat.txt` + свежий `iptables-save`). Теперь nat обслуживает
   только nft. Повторная проверка трафика.
3. **Персист по-человечески:** `systemctl enable --now nftables`. Отключить
   `netfilter-persistent` для nat (или вычистить nat из `rules.v4`), чтобы не
   было двух источников. **Тест ребутом** (согласовать окно) — главная цель всей
   затеи: после reboot nat поднимается сам.
4. **Откат на любом шаге:** `nft delete table ip relay` + восстановить
   legacy из бэкапа `iptables-restore < bak` — возврат в текущее состояние.

## 7. Влияние на Go-код

Генерация правил живёт в `service/portforward.go` (`AddForward`,
`RestoreRuVDSDNAT`, `persistIptables`) — собирает строки `iptables ...` и
гоняет по SSH. Для nftables:

- **Минимально:** оставить генератор iptables, но заменить `persistIptables`
  на запись `/etc/nftables.conf` + `nft -f` (атомарно) вместо
  `iptables-save`/`netfilter-persistent`. Чинит боль №1/№4 малой кровью.
- **Правильно:** генерить `map dnat_ports` из enabled-инбаундов БД и
  REDIRECT-строку из конфигурации туннеля; один шаблон → один `nft -f`.
  Чинит и №2 (атомарность). Больше работы, но это «настоящая» замена.
- Сохранить инвариант: строка REDIRECT 9443→29443 генерируется всегда и
  стоит до `dnat map`; 9443 не входит в map.

Рекомендуемый порядок: сначала «минимально» (быстрый выигрыш по ребуту),
потом «правильно» отдельной задачей.

---

## 8. Что nftables НЕ чинит (важно не путать)

- **ТСПУ-дроп fake-TLS** (причина майской аварии) — это DPI на проводе,
  пакетному движку RuVDS неподвластно. Лечится туннелем (уже сделано). nftables
  тут ни при чём — он лишь надёжнее носит REDIRECT в туннель.
- Блокировку портов 443/9443 — то же, ортогонально.
- UDP-проброс для Hysteria2 — можно заодно добавить в nft (`udp` правила),
  но это расширение скоупа, не обязательное для миграции.

## 9. Чек-лист проверки после миграции

- [ ] `nft list table ip relay` — REDIRECT 9443→29443 присутствует
- [ ] 44+ ESTABLISHED-сессий telemt живы (`ss` на Hetzner), `handshake timeout` ~0
- [ ] VPN-порты 443/2053-2058/4443/8444/8447 проксируются (счётчики map растут)
- [ ] SSH (22) не отрезан, UFW INPUT не сломан
- [ ] **Контрольный reboot RuVDS**: nat поднялся сам, MTProto и VPN живы без ручных действий
- [ ] `netfilter-persistent` больше не источник nat (отключён/вычищен)
- [ ] Откат проверен на сухом прогоне (шаг 1) до касания прода

---

### Итог одним абзацем

nftables нужен не ради моды, а чтобы **ребут перестал убивать релей**
(сломанный `netfilter-persistent` — корень инцидента 15 мая) и чтобы
переключения были атомарными. Перенос механический (§4), главный риск —
сосуществование с UFW и потеря REDIRECT-строки туннеля (§5). Делать
поэтапно с откатом на каждом шаге; к ТСПУ-аварии это не относится и её не
чинит — только делает уже сделанный фикс надёжнее на ребуте.
