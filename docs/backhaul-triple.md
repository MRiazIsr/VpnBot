# Тройной backhaul RuVDS → Hetzner

Замена единственного нестабильного плеча RuVDS→Hetzner на три независимо
переключаемых маршрута. **Настройки на телефонах не меняются вообще**: адрес,
порты, UUID, ключи Reality, SNI, short ID и MTProto secret остаются прежними.

## Схема

```
                       прежний адрес и прежние порты
   Телефон ───────────────────────────────────────────▶ RuVDS
                                                          │
                                       sing-box relay (L4, direct inbound)
                                       поток НЕ разбирается, ключей тут нет
                                                          │
                          ┌───────────────────────────────┴───────────────────────────────┐
                          │                                                               │
                     sel-vless                                                       sel-mtproto
              (443,2053…8447 → тот же порт)                                       (9443 → 9443)
                          │                                                               │
        ┌─────────────────┼─────────────────┐                     ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼                     ▼                 ▼                 ▼
   SOCKS5 :11080     SOCKS5 :11081     SOCKS5 :11082         SOCKS5 :11090     SOCKS5 :11091     SOCKS5 :11092
   primary           secondary         emergency             primary           secondary         emergency
   frp/TLS           vless+ws+tls      ssh -D (RuVDS→HZ)     frp/TLS           vless+ws+tls      ssh -D (RuVDS→HZ)
        │                 │                 │                     │                 │                 │
   IL residential    Yandex Cloud VM   инициирует Hetzner    (то же самое, но отдельными потоками)
        │                 │                 │
      wg1               Caddy             sshd
        │                 │                 │
        └─────────────────┴─────────────────┴──▶  Hetzner 10.9.0.1:<тот же порт>
                                                   Reality / ShadowTLS / MTProto
                                                   завершаются ТОЛЬКО здесь
```

Все три backhaul'а сходятся в одну точку — `10.9.0.1` (адрес Hetzner внутри
`wg1`). Это работает и для плеч, чей выход физически на самом Hetzner
(secondary, emergency): `10.9.0.1` там локальный адрес интерфейса, и он
существует независимо от того, подключён ли израильский узел.

## Почему именно так

**Почему `direct` inbound, а не DNAT.** DNAT прибивает назначение в ядре: одно
правило — один путь, переключать нечего. `direct` inbound sing-box принимает
сырой TCP и отдаёт его в outbound, который выбирается selector'ом. Никакого
разбора содержимого: `sniff` не включён, TLS на RuVDS нет, ключей Reality нет.

**Почему SOCKS5 у каждого плеча.** Единый интерфейс делает три очень разных
транспорта взаимозаменяемыми и, главное, позволяет health-checker'у проверять
каждое плечо **независимо от того, какое сейчас выбрано**. Без этого «проверка»
свелась бы к наблюдению за активным маршрутом, а про запасные мы бы узнавали
только в момент аварии.

**Почему по два адаптера на плечо.** Требование «не создавать один общий
мультиплексированный поток» соблюдается на двух уровнях: у VLESS и MTProto
разные SOCKS-порты (и разные outbound'ы, и разные selector'ы), а внутри
транспорта мультиплексирование отключено явно (`transport.tcpMux = false` у
frp, отсутствие блока `multiplex` у sing-box).

**Почему Reality не терминируется на RuVDS.** Ключи Reality на российской
площадке — это ключи, которые можно изъять вместе с машиной. Здесь RuVDS видит
только зашифрованный поток и не может ни расшифровать его, ни выдать себя за
сервер.

## Компоненты

### RuVDS

| Юнит | Что делает | Слушает |
|---|---|---|
| `sing-box-relay` | L4-relay, selector'ы, локальный API | публичные порты, API на `127.0.0.1:19090` |
| `sing-box-bh2` | адаптер secondary: SOCKS5 → vless+ws+tls → YC | `127.0.0.1:11081`, `127.0.0.1:11091` |
| `frps` | точка входа израильского узла | `0.0.0.0:7443`, прокси — на `127.0.0.1` |
| `backhaul-monitor` | health-checker, failover, гистерезис | — |
| `backhaul-fssh@vless`, `backhaul-fssh@mtproto` | `ssh -D` на Hetzner, SOCKS5 здесь | `127.0.0.1:11082`, `127.0.0.1:11092` |

### Hetzner

| Юнит | Что делает | Слушает |
|---|---|---|
| `wg-quick@wg1` | канал до израильского узла | `UDP :51821` |
| `backhaul-probe` | эндпоинт измерения | `10.9.0.1:18080` (только внутри WG) |
| `sing-box-bhws` | терминатор WSS-плеча | `127.0.0.1:21080` |
| `caddy` | `myvpn-api.online:8443/bhws` → sing-box-bhws | уже существующий :8443 |
| sshd (`Match User backhaul`) | принимает туннель с RuVDS, `PermitOpen` строго на backend-порты | :22 |

### Yandex Cloud

Виртуалка в `ru-central1` с Caddy. Почему не CDN — см.
[deploy/yc/README.md](../deploy/yc/README.md): WebSocket в Yandex Cloud CDN
включается только через тикет в поддержку, источник обязан отвечать за 5 секунд.

### Израильский узел

`frpc` + `wg-quick@wg1`. Узел за NAT/CGNAT — соединение всегда инициирует он.
Через туннель ходит только `10.9.0.0/24`: домашний трафик машины не затрагивается.

## Health checker

Проверка — не ping и не tcp-connect. Каждый цикл для каждого плеча и каждого
класса:

1. скачивание ≥128 KB через SOCKS5 этого плеча;
2. заливка ≥128 KB;
3. измерение фактической скорости, провал ниже `min_bytes_per_sec`;
4. детект зависания: если между двумя переданными байтами прошло больше
   `stall_sec`, соединение считается повисшим (TCP-сессия при этом жива —
   именно поэтому tcp-connect ничего не проверяет);
5. опционально — remote DNS: `CONNECT` уходит с `ATYP=DOMAINNAME`.

Решения:

| Событие | Условие |
|---|---|
| плечо признано мёртвым | `fail_threshold` провалов подряд (по умолчанию 3) |
| плечо признано живым | `recover_threshold` успехов подряд (по умолчанию 5) |
| уход вниз (failover) | немедленно, как только активное плечо мертво |
| возврат вверх (recovery) | прошёл `hold_down_sec` И плечо непрерывно здорово `stable_before_return_sec` |
| здоровых нет | остаёмся на текущем, не мечемся |

Уход вниз намеренно не придерживается hold-down: держать пользователей на
заведомо мёртвом канале ради «стабильности» бессмысленно, а демпфирование уже
обеспечено порогом из нескольких провалов подряд. Придерживается только
возврат — именно он способен вызвать flapping.

VLESS и MTProto считаются и переключаются полностью независимо: у них разные
selector'ы, разные outbound'ы, разные адаптеры и отдельные записи в состоянии.

Состояние переживает рестарт: `/var/lib/vpnbot/backhaul-state.json`. При
перезапуске `sing-box-relay` selector'ы сбрасываются на `default`, поэтому
монитор при старте **переустанавливает** их в сохранённое положение, а не
подхватывает то, что видит.

## Порядок развёртывания

```bash
cp deploy/backhaul/params.env.example deploy/backhaul/params.env
# заполнить: FRP_TOKEN, CLASH_API_SECRET, BHWS_UUID, YC_VM_IP
```

1. **Hetzner** — `deploy/hetzner/backhaul/install.sh params.env`
   Поднимает wg1, probe, sing-box-bhws, путь в Caddy, юниты reverse SSH.
   Печатает публичные ключи, которые нужны дальше.
2. **Yandex Cloud** — создать ВМ и A-запись (см. `deploy/yc/README.md`),
   затем `deploy/yc/install.sh params.env` на ВМ.
3. **RuVDS** — `deploy/ruvds/backhaul/install.sh params.env`
   Ставит relay на **staging-портах** (`порт + 30000`). Прод не задет.
4. **RuVDS** — `deploy/ruvds/backhaul/nftables-apply.sh params.env`,
   проверить доступ, затем `--confirm` (иначе откатится само через 10 минут).
5. **Проверка** — `scripts/backhaul/verify.sh params.env`
   и живой клиент на staging-порту.
6. **Перевод прода** — `deploy/ruvds/backhaul/promote.sh params.env`,
   проверить живым клиентом, затем `--confirm` (иначе откат через 15 минут).

Израильский узел подключается позже и отдельно: `deploy/il-node/install.sh`,
затем на RuVDS `PRIMARY_ENABLED=true` → `render-config.sh` → рестарт relay.
До этого момента `primary` помечен `disabled`, не попадает в selector'ы и не
опрашивается.

## Управление

```bash
scripts/backhaul/switch.sh status              # что активно, здоровье, скорости
scripts/backhaul/switch.sh vless secondary     # пин VLESS на secondary
scripts/backhaul/switch.sh mtproto emergency   # пин MTProto на emergency
scripts/backhaul/switch.sh vless auto          # снять пин
scripts/backhaul/switch.sh dry-run             # решения без переключений
scripts/backhaul/switch.sh probe               # разовая проверка всех плеч
scripts/backhaul/switch.sh logs 50             # история переключений
```

## Откат

| Что откатить | Команда |
|---|---|
| перевод прода на relay | `deploy/ruvds/backhaul/promote.sh --rollback` |
| правила nftables | `deploy/ruvds/backhaul/nftables-apply.sh --rollback` |
| всё целиком | `deploy/ruvds/backhaul/uninstall.sh params.env` |

Оба «ползучих» шага (nftables и promote) ставят таймер автоотката **до** того,
как что-то изменить: если связь с машиной пропадёт, состояние вернётся само.

## Какие профили идут через relay

Через RuVDS ходит всё, у чьего инбаунда `ServerAddress = 194.87.80.237`:

* класс `vless` — DE (443), DE-H2 (2053), DE-TCP (2054), DE-HU (2055),
  DE-XHTTP (2056), DE-WL-TCP (2057), DE-WL (2058), RU (2059), RU-TCP (2060),
  RU-STLS (8446);
* класс `mtproto` — telemt (9443), `server_address = 194.87.80.237`.

**Через relay НЕ идут и идти не должны: DE-VK (4443), DE-Yandex (8444),
DE-Sber (8447).** У них `ServerAddress` пуст, ссылка ведёт напрямую в Hetzner
мимо RuVDS — и ровно поэтому на 02.08.2026 они единственные работающие, пока
RuVDS лежит. Заводить их на RuVDS означало бы подчинить единственный живой
путь неисправному хосту, поэтому их нет в `RELAY_VLESS_PORTS`.

## Границы: чего эта схема не чинит

Тройной backhaul резервирует плечо **RuVDS → Hetzner**. Он не резервирует
плечо **клиент → RuVDS**. Если RuVDS не принимает TCP — а именно это
состояние наблюдается с 30.07.2026 — все 11 профилей выше мертвы независимо от
того, сколько backhaul'ов настроено позади. Сначала должен ожить RuVDS;
только после этого схема начинает приносить пользу.

## Что осталось публичным намеренно

Публичные порты на Hetzner (443, 2053–2060, 4443, 8444, 8446, 8447, 9443)
не закрываются: по ним ходят подписки, бьющие напрямую в Hetzner в обход
RuVDS, включая три единственных сейчас работающих профиля. Закрыть их можно
только после того, как все такие ссылки будут отозваны — это отдельное
решение, ломающее обратную совместимость. Новые backend-каналы (probe,
sing-box-bhws) доступны только через loopback и WG.
